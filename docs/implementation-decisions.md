# 실개발 확정 기준 · 2026-09-27

사용자의 디자인·업무 규칙 확인 후 진행하는 기준입니다.

## 디자인과 배포

- A 레이아웃, 흰색 표면과 연한 갈색 포인트.
- 최초 16px 컴팩트, 18/20/22px 선택과 저장 유지.
- 검토한 디자인을 main에 반영하고 기존 GitHub Pages 주소를 업데이트.
- 실서비스 API는 별도 개발 브랜치에서 단계적으로 연결. 공개 Pages는 계속 가상 데이터 시안.

## 권한

| 기능 | 대표 OWNER | 직원 STAFF |
|---|---|---|
| 약재 조회·등록·입고·처방 재료 확보 | 가능 | 가능 |
| 환자·처방·탕전 등 담당 업무 | 가능 | 가능 |
| 본인 휴가 신청·조회·철회/취소 요청 | 가능 | 가능 |
| 직원 휴가 승인·반려·취소 승인 | 가능 | 불가 |
| 직원 공용 달력 | 가능 | 가능 |
| 원장 경영·재무 자료 | 가능 | 불가 |

기존 시안의 데스크/조제 담당은 직원의 업무 예시이며 권한 등급을 추가하지 않습니다. 서버 계정의 OWNER/STAFF로 판정하고, 요청 본문이나 헤더의 임의 역할 값은 신뢰하지 않습니다. 직원에게 경영 데이터를 전송한 뒤 화면에서만 숨기는 방식은 사용하지 않습니다.

## 휴가

- 시작일·종료일을 모두 포함한 달력 일수. 주말·공휴일도 포함.
- 오전/오후 반차는 각각 0.5일. 신청 일수는 직접 입력하지 않음.
- 승인된 휴가만 달력에 표시. 취소 요청 중에는 유지하고 취소 승인 후 제외.
- 사유는 본인과 대표만 열람. 공용 달력에는 사유를 포함하지 않음.
- 연차 부여/잔여 한도/급여 정산은 이번에 확정한 범위가 아니며 자동으로 추가하지 않음.

## 개발 순서

1. 확정 디자인 배포.
2. TypeScript 점진 도입, 공통 업무 규칙 타입과 테스트, NestJS·Prisma·PostgreSQL 기반 구성.
3. 서버 로그인/세션과 두 역할 권한 검증, 휴가 저장·승인·달력 연결.
4. 직원 재고 입고·확보·차감 연결. 중복 요청과 동시 요청에서도 재고가 음수가 되지 않도록 트랜잭션 검증.
5. 나머지 CRM 흐름 연결 후 운영 환경과 백업 검증.

API/DB 접속 환경, 실제 계정 발급, 데이터 이전 및 메시지 업체 연결은 후속 단계입니다.
